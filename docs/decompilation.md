# Декомпиляция прошивки

Для бинарника `VEGA_vial_v1_01_20231201.bin` введён воспроизводимый первый
проход:

```text
python tools/decompile_firmware.py firmware/original/VEGA_vial_v1_01_20231201.bin
```

Он строит каталог предполагаемых функций из:

- адресов активных векторов;
- целей прямых `BL`/`BLX` переходов;
- адресной базы `0x08000000` и Thumb-режима.

Имена пока имеют два уровня достоверности:

- подтверждённые роли: `reset_startup`, `svc_rtos`, `systick_rtos`;
- рабочие гипотезы: `irq_vector_NN` и `sub_XXXXXXXX`.

Полный машинный листинг генерируется отдельно через установленный ARM
`objdump`. Он сохраняется локально в `analysis-output/full-thumb-disassembly.txt`
и не включается в Git из-за размера.

Текущий запуск на образе дал `236` кандидатов на начало функций. Это верхняя
оценка: автоматический поиск по `BL` также захватывает отдельные ложные цели
из областей данных. После проверки прологов, ветвлений и `BX LR` каталог будет
сокращён до подтверждённых функций.

Из уже подтверждённых участков:

- `reset_startup` — копирование `.data`, очистка BSS и запуск таблиц
  инициализаторов;
- `svc_rtos` — работа с PSP/BASEPRI, часть системного переключения;
- `systick_rtos` — системный счётчик и обслуживание списка таймеров/ожиданий;
- `vector[30] -> 0x08009959` — активный IRQ-кандидат, работающий с флагами
  состояния и рабочей структурой;
- `vector[31] -> 0x08008BD1`, `vector[40] -> 0x08009601`,
  `vector[42] -> 0x08009741`, `vector[46] -> 0x08009DB1`,
  `vector[48] -> 0x08009DC5`, `vector[51] -> 0x08008BD5` — следующие
  периферийные IRQ-кандидаты для разметки.

## Первая карта периферийных связок

Скрипт [`tools/peripheral_xrefs.py`](../tools/peripheral_xrefs.py) разрешает
PC-relative `LDR` к реальным адресам периферии. На текущем образе найдено 57
таких ссылок:

| Область образа | Наблюдение | Рабочая гипотеза |
|---|---|---|
| `0x080061E0–0x08006300` | RCC, I2C2, UART1, UART3, QSPI | общая инициализация HAL и структур драйверов |
| `0x0800661C–0x08008110` | RCC, USB, GPIOC | низкоуровневый системный/USB слой |
| `0x08008A44–0x08009A14` | многочисленные USB-регистры | USB peripheral driver, включая endpoint/status логику |
| `0x0800A57C–0x0800A742` | десять ссылок на GPIOB | GPIO-конфигурация и служебные операции с портом |

### Найдена реальная инициализация UART

В отличие от одних только ссылок на HAL, участок `0x08006900–0x080069E0`
содержит исполняемую настройку последовательного интерфейса:

- в RAM-структуру по адресу `0x20000D68` записывается `115200` (`0x1C200`);
- затем настраивается `GPIOC` (`0x40000800`);
- через объект драйвера по `r7 + 0x154` программируются поля UART-периферии;
- перед этим проверяется флаг однократной инициализации, поэтому это выглядит
  как startup драйвера, а не случайная константа в таблице.

Сопоставление объектов уточняется по ранней инициализации около
`0x08006218–0x0800622A`: объект `0x20000DA0` получает базу `UART1`
(`0x40003800`), а объект `0x20000EFC` — базу `UART3` (`0x40008400`).
Код настройки `115200` обращается к аппаратному объекту через `r7 + 0x154`,
где `r7` в этом контексте указывает на второй объект. Поэтому наиболее
вероятная идентификация — **реально запускается UART3 на 115200 бод**.
Это сильная улика отдельной межконтроллерной линии, но ещё не доказательство
обмена именно с HFD80: нужны xref на runtime TX/RX, callback'ы или логический
анализ линий.

Есть и runtime-признак, а не только startup: общий обработчик
`0x08009C6C` читает status/data-регистры UART, складывает принятые байты в
кольцевой буфер и обслуживает TX/RX interrupt flags. Два IRQ-wrapper'а
`0x08009DB0` и `0x08009DC4` вызывают его для объектов `0x20000DA0` и
`0x20000EFC` соответственно. Следовательно, оба последовательных драйвера
имеют рабочий interrupt path; для второго объекта это уже серьёзный кандидат
на межплатную связь с дисплейным контроллером. Пока не найден только верхний
уровень: формат пакета, инициатор обмена и вызов TX из прикладочного цикла.

Вызовы `0x08009248`, встречающиеся внутри этого обработчика, не являются
передачей данных: функция работает со списками ожидания/событиями RTOS.
Поэтому их нельзя считать найденными командами HFD80. На текущем проходе
прикладочный TX-вызов UART3 остаётся отдельной задачей поиска.

### Найден прикладочный TX UART3

Такой вызов найден. В функциях около `0x08001A48` и `0x08001AAA` прошивка
создаёт короткие пакеты и передаёт их в потоковый API `0x08008500`:

```text
stream = 0x20000F2C = 0x20000EFC + 0x30
send(stream, packet, 3, timeout = 0xFFFFFFFF)
```

`0x20000EFC` — объект `UART3`, поэтому `0x20000F2C` является его встроенным
потоковым/буферным под-объектом, а не отдельным USB endpoint или RGB-буфером.
Это окончательно связывает найденную прикладочную логику с TX UART3.

Для функции `0x08001A48` восстановлен кандидат пакета:

```text
[0x03, state, state + 0x03]
```

где `state` принимает значения `1`, `2` или `3`; третий байт вычисляется
простым сложением по модулю 256. Функция вызывается из `0x08004722` и
`0x08007C28`, то есть пакет отправляется из рабочего кода, а не только при
инициализации. Семантика значений `state` ещё требует сопоставления с
переключением режимов/индикацией, но это уже первый обнаруженный транспортный
протокол между основной логикой и вероятным вторичным контроллером.

Отдельная функция `0x08001A88` всегда формирует фиксированный пакет
`[0x03, 0x02, 0x05]`. Она вызывается при обработке специального значения
`0x00AA` в двух ветках keycode/event dispatcher (`0x08004168` и
`0x080046BC`). Поэтому `0xAA` — кандидат на событие переключения/сброса
режима вторичного контроллера, а не обычную клавишу.

### Вторая команда: статус клавиатуры/индикаторов

Соседняя функция `0x080019A4` использует тот же UART3 stream и отправляет
другой трёхбайтный пакет:

```text
[0x02, flags, flags + 0x02]
```

Перед формированием `flags` она трижды вызывает `0x08001810` и проверяет биты
`0`, `1` и `2` возвращаемого состояния — наиболее вероятно Num Lock, Caps Lock
и Scroll Lock. Дополнительные биты собираются из RAM-флагов; их назначение
пока не закрепляем. Функция вызывается из фонового цикла около `0x08007C20`
после таймера примерно `500 ms`, поэтому это похоже на периодическую
синхронизацию статуса с вторичным контроллером.

`0x08001810` читает состояние через callback-объект в RAM, а не из UART:
это общий интерфейс получения LED/клавиатурного статуса. Тем самым разделены
источник данных и транспорт: состояние формируется основной логикой, затем
передаётся вторичному контроллеру по UART3.

Текущая минимальная карта протокола UART3:

| Первый байт | Формат | Рабочее назначение |
|---:|---|---|
| `0x02` | `[02, flags, flags+02]` | состояние индикаторов/клавиатуры |
| `0x03` | `[03, state, state+03]` | режим или состояние платформы |

Суммирующие байты выглядят как простая контрольная зависимость, но пока не
утверждаем, что это полноценная checksum: в найденных пакетах сумма использует
первый байт команды как добавку.

Прямых прикладочных вызовов чтения из UART3-потока не найдено. RX interrupt
и кольцевой буфер существуют, но parser команд от вторичного контроллера в
этом образе пока не выделен; текущая прошивка выглядит преимущественно как
односторонняя передача статусов к нему.

Особенно показателен кластер около `0x080092EA–0x080095F2`: там есть
множество операций с регистрами USB, но также таблицы состояний и вызовы
через указатели. Это главный кандидат для восстановления USB/Vial пути.

Участок `0x0800A57C` вызывает низкоуровневую функцию примерно с параметрами
`(GPIOB, mask, mode/config)` и использует маски `0x08`, `0x20`, `0x10`, затем
`0x1A82` и `0x0282`. Пока корректнее назвать его `gpiob_config_candidate`:
сам по себе этот фрагмент не доказывает matrix scan.

## Поиск matrix scan

Первичная проверка не подтвердила сканер в найденных GPIO-кластерах:

- `0x080068BE` и `0x08006AD6` — настройка GPIOC с регистрами конфигурации;
- `0x0800A58A` — настройка GPIOB через маски и режимы;
- `0x08008B92` — общий низкоуровневый GPIO-конфигуратор;
- `0x08008B18` — объектный транспортный код, связанный с USB, а не GPIO-сканер.

Перспективен диапазон `0x080067D0–0x08006A60`. В нём есть циклы на 17 и 6
элементов по таблицам указателей, а также временная работа с GPIOA. Пока это
выглядит как аппаратная/драйверная инициализация, но именно здесь могут быть
таблицы линий платы. Следующий критерий проверки — наличие внутри вызываемых
функций чтения входного регистра и повторного прохода с изменением номера
строки. До такой проверки называть участок `matrix_scan` преждевременно.

### Подтвержденные таблицы матрицы

Дальнейший разбор literal pool показал, что адреса `0x08006A88` и
`0x08006A8C` указывают на две таблицы GPIO-дескрипторов:

```text
columns[17] = {
    C1, C2, C3, A0, A1, A2, A3, A4, A5, A6, A7,
    C4, C5, B0, B1, B2, B10
};

rows[6] = { B15, C6, C7, C8, C9, B14 };
```

В бинарнике это хранится как адреса вида `0x40000801` или `0x4000040F`:
база GPIO плюс номер вывода. Первая таблица содержит ровно 17 элементов,
вторая ровно 6. Циклы в `0x08006770` обходят их соответственно 17 и 6 раз,
передавая каждый дескриптор в `0x08002A6E`.

`0x08002A6E` извлекает младшие четыре бита как номер вывода, очищает их для
получения базы порта и вызывает `0x08008B92` с маской и режимом GPIO. Это
подтверждает назначение таблиц как аппаратной конфигурации клавиатурной
матрицы, а не случайной таблицы периферии.

Уровень уверенности:

- наличие двух наборов GPIO: **точно**;
- размеры 17×6: **точно**;
- назначение как columns/rows: **очень вероятно**, совпадает с порядком
  циклов и физическим форматом KD85;
- полярность диодов и точная функция сканирования: ещё нужно подтвердить по
  чтению входов и обработке debounce.

### Энкодер и служебные режимы KD85

Матрицу считаем источником обычных клавиш. Отдельно учитываем:

- энкодер громкости с двумя фазовыми входами `ENC_A` и `ENC_B`;
- кнопку на валу энкодера, если она электрически присутствует на плате;
- Fn-сочетания для эффектов подсветки, яркости и переключения Win/Mac.

Два фазовых сигнала энкодера не следует добавлять в таблицу `17×6`: они могут
быть отдельными GPIO главного MCU, линиями вторичного контроллера или событиями,
передаваемыми по шлейфу. В бинарнике их будем искать по двум взаимосвязанным
входам, обработке переходов состояний и последующем изменении значения
громкости/режима.

Сочетания подсветки и Win/Mac — не отдельные физические клавиши, а обработка
слоёв/keymap. Для них нужны восстановление keymap-таблиц, layer state и
числовых action-кодов.

### Восстановленная keymap-таблица

В области `file+0xB5D8` находится таблица из `6×17` 16-битных QMK keycodes.
Она начинается с узнаваемых стандартных кодов:

```text
layer 0, row 0: KC_ESC, KC_F1 ... KC_F12, KC_PSCR, KC_SLCK, KC_PAUS, ...
layer 0, rows 1–5: цифры, буквы, модификаторы, пробел и навигация
```

Это подтверждает, что таблица GPIO и таблица keymap используют одинаковую
геометрию `6×17`. В области `file+0xB6A4` находится ещё один слой/вариант
таблицы: там много `0x0001` (`KC_TRNS`) и специальные действия.

В найденных специальных значениях присутствуют:

- `0x7823`, `0x7827`, `0x7828`, `0x7829`, `0x782A` — QMK RGB/underglow
  управление;
- `0x5223` — код моментального перехода/удержания слоя QMK-диапазона;
- `0x5240` — специальное layer-action значение старой/кастомизированной
  таблицы keycodes.

Таким образом, сочетания подсветки уже присутствуют в keymap, а не только в
прошивочной логике. Точную привязку всех специальных кодов к легендам нужно
сопоставить с версией QMK, использованной производителем.

### Экран и GIF

В основном образе не найдены сигнатуры `GIF87a`, `GIF89a`, PNG, JPEG или BMP.
Следовательно, сами изображения в этот бинарник не встроены. Остаются два
рабочих варианта:

1. GIF-файлы хранятся во внешней flash `PY25Q128HA`/`P25D80SH`, а MCU
   передаёт экранному контроллеру команды чтения или обновления;
2. производительское приложение передаёт анимацию по USB во второй контроллер
   `HFD80CP100`, а тот уже пишет данные в свою память/дисплей.

В образе действительно присутствуют ссылки на `QSPI`, `UART1`, `UART3` и
`I2C2`, но это пока только доказательство наличия драйверных объектов. Нужно
отделить общую ChibiOS-инициализацию от функций, которые реально передают
данные после старта. Для экранного протокола приоритетны длинные циклы
передачи, блоки с длинами/смещениями flash и вызовы UART/I2C после USB-команд.

### Уточнение по QSPI, RGB и I2C

Статические xref дают более точное разделение:

- `0x0800A57C` вызывается из `0x08006340`, непосредственно перед первым
  чтением внешней flash. Функция настраивает GPIOB и переводит несколько линий
  в альтернативный режим; это сильный кандидат на инициализацию QSPI/NOR, а не
  на интерфейс TFT.
- `0x0800A704` вызывается из `0x080021C0`, рядом с настройкой 24 элементов
  RGB-таблицы и отправкой цветовых/режимных параметров. Она настраивает две
  линии GPIOB и, вероятнее всего, относится к драйверу подсветки.
- Единственная прямая ссылка на базу `I2C2` находится в общей структуре HAL
  около `0x08006206`. Надёжных последующих записей/чтений регистров I2C2,
  адреса ведомого или буфера обмена в приложенческой части не найдено.

Промежуточный вывод: текущий бинарник уверенно содержит рабочие QSPI/NOR и
RGB-пути, но не показывает активный I2C-протокол дисплея. Если TFT управляется
из этой прошивки, его транспорт следует искать среди UART/USB или в отдельном
контроллере, а не в уже найденном I2C2 startup path.

### Подтверждение отдельного RGB-драйвера

Участок `0x0800A2DC` содержит характерную последовательность записи в
многоканальный LED-контроллер через `0x08009FCC`:

```text
write(reg=0xFE, value=0xC5)
write(reg=0xFD, value=0x00)
for reg = 0..23:  write(reg, 0x00)
write(reg=0xFE, value=0xC5)
write(reg=0xFD, value=0x01)
for reg = 0..191: write(reg, 0x00)
write(reg=0xFE, value=0xC5)
write(reg=0xFD, value=0x03)
write(reg=0xFD, value=0x0F)
write(reg=0xFD, value=0x10)
write(reg=0x01, value=0xFF)
write(reg=0x00, value=0x01)
```

Последовательности с 24 и 192 регистрами, bank/page select через `0xFD` и
служебный регистр `0xFE` намного больше похожи на внешний RGB LED driver, чем
на TFT-контроллер. Это хорошо согласуется с двумя микросхемами `HFD5501L` на
плате. Точная модель и электрический интерфейс пока не подтверждены, но
функциональная роль этого кода теперь имеет высокую уверенность.

Дополнительный xref уточняет границу подсистемы: объект в RAM по адресу
`0x200032AC` используется цепочкой `0x08009FCC -> 0x0800A778`, а
`0x08009FCC` вызывается из RGB-инициализации. Поэтому этот объект нельзя
использовать как доказательство UART-связи с HFD80: это отдельный объект
низкоуровневого LED/serial-like драйвера.

### Поиск связи с отдельным контроллером

#### Аудит возможных третьих каналов

После обнаружения UART3 проверены остальные интерфейсы, которые теоретически
могли бы вести непосредственно к TFT:

| Канал | Статический статус | Оценка роли |
|---|---|---|
| `UART3` | startup `115200`, IRQ, прикладочный TX пакетов `02/03` | межконтроллерный статусный канал, вероятно WB32 → HFD80 |
| `UART1` | объект и IRQ-драйвер существуют, отдельного прикладочного TX не найдено | запасной/служебный порт или вариант платформы |
| `I2C2` | есть только HAL literal `0x40008800` | реальный пользователь пока не установлен |
| `QSPI` | активные read/program/erase операции | внешний NOR/storage, не доказан TFT-транспорт |
| RGB serial-like driver | объект `0x200032AC`, цепочка `0x08009FCC` | внешний LED-драйвер, не TFT |
| USB raw HID | один основной Vial-интерфейс | USB подключён к WB32-ветке |

Таким образом, третий WB32-канал к TFT пока не подтверждён. Наиболее
правдоподобная архитектура сейчас: WB32 передаёт HFD80 короткие статусы по
UART3, а сам HFD80 напрямую управляет TFT по своему SPI/8080-подобному или
другому локальному интерфейсу. Для загрузки GIF тогда нужен отдельный
производительский USB command path/образ либо переадресация, отсутствующая в
исследованном Vial-бинарнике.

### Найденный локальный референс Dark Project

В системе обнаружена установленная утилита:

`C:\Program Files (x86)\Dark Project\Vega Screen Software\Vega Screen Software.exe`

Она запускается с заголовком **KD85A Vega Screen Software**. Это сильная
зацепка для восстановления протокола экранчика: в PE-файле присутствуют
отдельные LCD/TFT/GIF-классы, `GetImageRGB565Data`, `SaveGIFImageFile`, поля
`gif_headlength`, `gif_maxframes`, `gif_count`, а также динамическая загрузка
`hid.dll` и вызовы `HidD_GetFeature`/`HidD_SetFeature`. Следовательно,
производительский загрузчик экрана, вероятно, использует HID feature reports,
а изображение передаётся как RGB565-кадры или их блоки.

Конфигурация этой установки ожидает `VID:PID = 05AC:024F`, интерфейс
`MI_03`, тогда как исследуемая QMK/Vial-прошивка сейчас определяется как
`FFFE:0030`, usage page `FF60`, interface 1. Поэтому найденная программа не
является доказательством совместимости с текущим образом: это референс
протокола/формата и, возможно, программа для близкой аппаратной ревизии.
Комплектная прошивка из каталога имеет имя
`INFI75-80键-RGB三模-HFD2201KBA_V1.05_20231104_0x6AF6.exe`, размер 1,892,352
байта, SHA-256
`8B836556D3B80018EEC7A09A4CBE25C5AAABA0EBF6EE4623DAD8EED5F99B7F5C`;
она пока не сопоставлена с KD85 безымянной платой и не должна прошиваться в
неё.

На текущем этапе безопасный план такой: статически извлечь из приложения
формат feature-report и размеры кадров, затем при необходимости записать
тестовый кадр только через штатную утилиту, предварительно убедившись, что
она видит именно нашу клавиатуру. Угадывание команд записи в raw HID
`0x04..0x0C` или прямую память TFT без этой проверки отложено: в QMK/Vial
ветке среди найденных read-only ответов экранный транспорт не подтверждён.

### Первый live-перехват экранной утилиты

Важно: у утилиты обнаружен отдельный USB-девайс `05AC:024F SONiX VEGA` с
несколькими HID-коллекциями. Конфигурация программы явно выбирает
`VID_05AC&PID_024F&MI_03`; это не основной `FFFE:0030` Vial-интерфейс WB32.

Через Frida перехвачены вызовы `HidD_SetFeature` и `DeviceIoControl` у
запущенной `KD85A Vega Screen Software`. При попытке загрузить добавленный
однокадровый белый GIF программа действительно обращается к клавиатуре, но
передаёт только 65-байтные служебные отчёты. Входной буфер
`DeviceIoControl` побайтно дублирует буфер `HidD_SetFeature`, то есть это два
пути одного и того же HID-обмена, а не отдельный поток пикселей.

Наблюдались следующие семейства:

```text
00 04 18 00 ...
00 04 28 00 ... 01 00 ...
00 5A 01 5A 1A 08 12 13 xx xx 00 02 ... AA 55
00 04 02 00 ...
00 04 17 00 ... 01 00 ...
00 00 00 00 00 00 00 02 07 02 ... AA 55
00 04 72 01 ... 10 00 ...
```

Для белого кадра RGB565-буфер (`FF FF` повторяющиеся по пикселям) в
перехваченных отчётах не появился; вызовов `WriteFile` с крупным буфером также
не было. Это означает, что утилита прошла служебное рукопожатие, но не начала
передачу изображения для текущего `VID:PID = FFFE:0030`, либо передача
откладывается до специального подтверждения/режима второго контроллера.
Во втором захвате, выполненном уже после нажатия кнопки загрузки, получено
22 успешных `HidD_SetFeature`-отчёта на одном дескрипторе. Состав отчётов
совпал с указанными служебными семействами; RGB565-потока и больших
`WriteFile`-буферов в процессе `Vega Screen Software.exe` не обнаружено.
`DeviceIoControl` использует коды `0xB0191`/`0xB0192` и дублирует те же
65-байтные буферы. Следовательно, это подтверждает правильный VID/PID и
интерфейс служебного обмена, но ещё не локализует сам транспорт кадров.

Позднейший перехват с расширенным логированием уточнил транспорт кадров:
официальная утилита вызывает `WriteFile` с буфером длиной `4097` байт. Первый
байт `00` — HID report ID, следующие `4096` байт совпадают с данными
interrupt OUT из USBPcap. В одном тестовом запуске зафиксировано 16 таких
вызовов для одного 64-КиБ слота. Поэтому предыдущая попытка отправки ровно
4096 байт была некорректна: в ней отсутствовал начальный report ID.

Наиболее вероятные варианты, которые остаются проверить: нативные
`NtDeviceIoControlFile`/`NtWriteFile`, другой HID-интерфейс того же
`05AC:024F`, либо отдельный драйверный/контроллерный путь, не проходящий
через обычный HID report API. Ручная отправка неизвестных команд пока не
делается: назначение полей и контрольных байтов `AA 55` ещё не установлено.

### USBPcap: найден реальный поток кадров

После перезагрузки USBPcap был запущен с повышенными правами. В захвате
`analysis-output/elevated-test.pcap` найдено устройство `bus 2, address 4`,
которое ранее по дескриптору определилось как `05AC:024F SONiX VEGA`.
Критическая последовательность идёт не через feature report, а через HID
interrupt endpoints:

| Направление | Endpoint | Размер | Количество |
|---|---:|---:|---:|
| ПК → VEGA | `0x03 OUT` | `4096` байт | `32` |
| VEGA → ПК | `0x84 IN` | `64` байта | `32` |

Итого передано `131072` байта данных изображения. Это ровно два блока по
`65536` байт. В каждом блоке:

```text
0x0000..0x00FF   256-байтный заголовок/служебная область
0x0100..0xFDBF   240 × 135 × 2 = 64800 байт RGB565
0xFDC0..0xFFFF   выравнивание до 64 KiB
```

Это очень сильное подтверждение параметров TFT: разрешение `240×135`,
формат пикселя RGB565 и двухкадровая загрузка. Первые байты блока имеют вид
`01 19 FF FF ...`; это уже не RGB565, а транспортный заголовок. Ответы на
`0x84 IN` начинаются с `01 5A 02` и повторяются после каждого блока, то есть
служат подтверждением приёма/готовности.

Из потока восстановлены два тестовых кадра; при интерпретации 64800 байт
как RGB565 оба кадра дают осмысленное изображение. Следовательно, найден не
просто случайный bulk-трафик, а полный рабочий протокол загрузки экрана.
В повторно проверенном захвате фильтр USB HID даёт 32 ненулевых OUT-записи
по 4096 байт (между ними есть нулевые continuation-кадры USBPcap), а не 64
логических записи. 32 × 4096 = 131072 байта.

Оба 64-КиБ блока имеют одинаковый заголовок: `01 19`, затем `FF` до байта
`0xFF`. Остаток после RGB565 (`0xFDC0..0xFFFF`, 480 байт) также полностью
заполнен `FF`, поэтому в этом захвате это выравнивание/заполнитель, а не
скрытый хвост изображения. Все 32 ответа `0x84 IN` одинаковы и начинаются
`01 5A 02`, что позволяет уверенно считать их ACK/статусом готовности.

Для повторения анализа добавлен пассивный инструмент
`tools/analyze_tft_pcap.py`. Он читает только pcap через `tshark`, извлекает
слоты и RGB565-кадры и не открывает HID-устройство. `tools/tft_protocol.py`
содержит такую же офлайн-модель 64-КиБ слота и намеренно не содержит кода
отправки.

Отдельный контроллер всё ещё может присутствовать в архитектуре, однако в
данном WB32-образе прямой прикладной транспорт к нему пока не выделен:

- `I2C2`, `UART1` и `UART3` встречаются в startup/HAL-структурах;
- для `UART3` найден исполняемый startup-путь с параметром `115200` и
  настройкой `GPIOC`; это уже не просто literal pool, но пока ещё не полная
  реконструкция протокола HFD80;
- `0x08009C6C` — общий UART IRQ-обработчик с RX-кольцевым буфером и TX/RX
  флагами; wrappers `0x08009DB0` и `0x08009DC4` обслуживают оба UART-объекта;
- после инициализации не найден устойчивый xref из USB/Vial или основного
  рабочего цикла к транзакционным функциям этих периферий;
- `0x08008B18` вызывается из USB endpoint/очередей и не является UART/I2C;
- `0x08009FCC` принимает короткие пары байт и вызывается RGB-инициализацией,
  поэтому сейчас классифицируется как LED-driver transport;
- объект `0x200032AC` связан именно с этой RGB-цепочкой;
- задействованные GPIO уже в значительной степени объясняются матрицей,
  QSPI и RGB.

Рабочие варианты остаются такими:

1. HFD80 работает автономно и имеет собственную прошивку, а WB32-бинарник
   управляет только матрицей, USB/Vial, flash и RGB;
2. связь идёт через небольшой GPIO-протокол в неразмеченном участке, который
   ещё не удалось отделить от очередей событий;
3. связь находится в другом образе/режиме производителя, а не в обычной Vial
   прошивке;
4. один из ранее предполагаемых чипов является не вторым MCU, а частью
   автономного LED/display subsystem.

Следующий статический тест — построить карту всех записей в GPIOA/B/C и
сопоставить оставшиеся линии с контактами шлейфов. Это даст шанс найти
однобитный или многобитный inter-controller protocol без предварительного
знания его названия.

### Найденный драйвер внешней NOR-flash

В диапазоне `0x080020F4–0x08002166` находится универсальный SPI/QSPI
транзакционный слой. Его рабочая сигнатура восстановлена приблизительно как:

```c
flash_xfer(uint8_t command,
           uint32_t address,
           const void *buffer,
           uint32_t length);
```

Выше него обнаружены специализированные операции:

| Адрес | Рабочее имя | Признак |
|---:|---|---|
| `0x08003430` | `flash_wait_ready` | опрос status и ожидание завершения |
| `0x0800346C` | `flash_sector_erase` | write-enable и команда `0xD8` |
| `0x080034A8` | `flash_read` | команда `0x03`, адрес, буфер и длина |
| `0x080034FA` | `flash_page_program` | команда `0x02`, блочная запись |
| `0x080035B0` | `flash_storage_init` | проверка/инициализация служебной области |

Также видны команды `0x05` (read status), `0x06` (write enable) и сектор
размером `0x1000`. Инициализация ограничивает текущую служебную область
примерно `0x2000` байтами, что больше похоже на EEPROM/wear-leveling или
настройки, чем на хранение GIF.

Промежуточный вывод: связь с внешней flash подтверждена, но именно GIF-хранилище
в этом образе пока не доказано. Следующий критерий — найти USB/vendor-команду,
которая вызывает `flash_read`/`flash_page_program` с большими адресами и
длинами, либо найти отдельный транспортный слой к `HFD80CP100`.

## USB и Vial/raw HID

В области USB-дескрипторов найдены два важных признака:

- raw HID usage page `0xFF60`, usage `0x61/0x62/0x63`;
- input и output reports по `32` байта (`REPORT_COUNT = 0x20`, `REPORT_SIZE = 8`).

Строка идентификации `vial:f64c2b3c` присутствует в UTF-16LE в районе
`file+0xAE00`. Это согласуется с Vial-совместимым raw HID каналом QMK.

Для дальнейшего сопоставления полезны стандартные command ID Vial/QMK:

```text
01 protocol version
02/03 keyboard value get/set
04/05 dynamic keymap get/set keycode
06 keymap reset
0C–10 macro buffer operations
11 layer count
12/13 keymap buffer get/set
14/15 encoder map get/set
```

### Найденный обработчик vendor HID

Обработчик найден в диапазоне `0x08006F94–0x08007B90`. Перед входом в него
низкоуровневый USB callback принимает ровно `0x20` байт. Обработчик затем:

1. проверяет фактически принятый размер (`0x08006FA0–0x08006FD4`);
2. читает байт команды из входного отчёта;
3. выбирает ветку через таблицу `TBH` по адресу `0x08006FE2`;
4. формирует ответ в локальном 32-байтном буфере;
5. отправляет его через `0x0800197C`, который вызывает endpoint callback
   из USB-объекта.

Подтверждённые ветви диспетчера:

| ID | Адрес ветви | Наблюдаемое действие |
|---:|---:|---|
| `0x00` | `0x080077C2` | чтение блока из служебного storage, ответ длиной 8 байт |
| `0x01` | `0x080077EA` | формирование/чтение идентификационного ответа |
| `0x02` | `0x080077FC` | операция с параметрами/служебными данными |
| `0x03` | `0x08007830` | чтение значения по 16-битному адресу/индексу |
| `0x04` | `0x08007862` | работа с 16-битными параметрами и storage |
| `0x05` | `0x08007892` | очистка/подготовка 28-байтного ответа |
| `0x06` | `0x080078C0` | системное состояние и версия/таймер |
| `0x07` | `0x080078D4` | работа с состоянием/счётчиками |
| `0x08` | `0x08007932` | сброс/очистка состояния |
| `0x09` | `0x0800793A` | запись блока параметров |
| `0x0A` | `0x0800797A` | поиск записи в таблице по 16-битному ключу |
| `0x0B` | `0x080079B0` | поиск и вызов обработчика записи |
| `0x0C` | `0x08007A0C` | отдельная служебная операция, вызывает `0x080031F0` |
| `0x0D` | `0x08007A12` | поддиспетчер macro/storage по байту `data[2]` |

У `0x0D` обнаружена внутренняя таблица переходов по `data[2]`:

| `data[2]` | Адрес | Наблюдение |
|---:|---:|---|
| `0` | `0x08007A28` | очистка/нулевая подготовка ответа |
| `1` | `0x08007A42` | формирование 10-байтного параметра |
| `2` | `0x08007A64` | преобразование/запись 16-битных полей |
| `3` | `0x08007AC8` | чтение записи длиной 10 байт |
| `4` | `0x08007AF0` | запись записи длиной 10 байт |
| `5` | `0x08007B2E` | чтение альтернативного блока длиной 10 байт |
| `6` | `0x08007B52` | запись альтернативного блока длиной 10 байт |

Для подкоманд `3–6` индекс берётся из `data[3]`, допускаются значения `0–31`,
а адрес записи вычисляется как `base + 10 * index`. Это объясняет вызовы
`0x0800A0AC`/`0x08009FE8` и подтверждает USB → внешний NOR flash связь.
Пока это следует называть macro/storage path: прямого доказательства, что
эти 10-байтные записи являются именно keymap или кадрами дисплея, нет.

Пока не найден отдельный vendor ID, который передаёт большие блоки изображения
или вызывает транспорт к `HFD80CP100`. При этом UART3 теперь подтверждён как
канал коротких статусных пакетов, но путь `USB/Vial -> UART3` для больших
данных не найден. Это оставляет три основные гипотезы:

1. изображения находятся в другой области памяти/другом контроллере;
2. производитель использует отдельный режим/приложение, не включённый в этот
   Vial-диспетчер;
3. второй контроллер имеет собственную USB-ветку/режим, который не представлен
   в основном WB32 raw-HID descriptor.

## Как будем давать имена

Имя закрепляется только после проверки нескольких признаков:

| Рабочее имя | Что должно подтвердиться |
|---|---|
| `usb_irq` | доступ к USB-регистрам, endpoint/status-поля, вызовы HID-логики |
| `vendor_hid_dispatch` | сравнения байта команды, длина 32-байтного отчёта, таблица ответов |
| `i2c2_transport` | записи/чтения I2C-регистров, START/STOP, адрес ведомого |
| `gpio_matrix_scan` | повторяющийся цикл по линиям, чтение входов и запись выходов |
| `key_debounce` | маски/счётчики стабильности и переходы состояний |
| `rgb_update` | длинные последовательности записей цветов или таймингов |
| `vial_protocol` | vendor HID dispatch и известные Vial/VIA структуры |

## Ограничение результата

Это восстановление логики, а не получение исходного проекта. Сохранятся
условия, циклы, обращения к памяти и вызовы, но не исходные имена, типы и
комментарии. Поэтому каждое имя будет сопровождаться уровнем уверенности и
xref на подтверждающие инструкции.
